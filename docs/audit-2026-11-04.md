# Audit Watermap du 4 novembre 2026

Audit et corrections réalisés sur `dev`, sur le Raspberry Pi, à partir du commit `5a7d388`. Aucune fusion vers `main` ni aucun déploiement sur le VPS. Le cycle de validation est enregistré dans `/home/yann/AGENTS.md` et dans les README : recette sur le RPi, validation de Yann, fusion vers `main`, puis déploiement de `main` sur le VPS.

## Périmètre

Revue des routes Flask, comptes, sessions, formulaires, imports GPX/KML et HTTP, traitements asynchrones, calcul géographique, cartes et JavaScript, dépendances Python, images/Compose et scripts de préparation, sauvegarde et restauration. Tests automatisés sur données temporaires et test dans l'image Python 3.12 ARM64, exécutée sans privilèges et en lecture seule. Les services et données de production sur le VPS n'ont pas été modifiés.

## Constats et corrections

| Priorité | Constat avant correction | Correction et vérification |

| Haute | Les jetons de réinitialisation étaient valables jusqu'à leur expiration même après usage ou changement de mot de passe. | Jetons signés avec un sel spécifique et liés à la version du mot de passe ; mise à jour conditionnelle en base pour éviter deux consommations concurrentes. Tests de réutilisation et d'invalidation. |
| Haute | Les sessions existantes restaient utilisables après un changement de mot de passe. | Identifiant de session lié au condensat de la version du mot de passe. Les sessions des autres navigateurs sont invalidées ; le navigateur qui change son mot de passe conserve sa connexion. Les anciens mots de passe PBKDF2 restent compatibles. |
| Haute | Chaque import pouvait créer un thread supplémentaire, sans plafond global. Les fichiers et le travail CPU n'avaient pas de quotas adaptés. | Deux traitements maximum, sans file d'attente illimitée ; réponse 503 si occupé. Fichiers/téléchargements limités à 20 Mo, 100 000 points, budget de comparaisons géographiques, historique de 200 statuts et expiration lors des imports. Réserve disque de 512 Mo, cartes générées limitées à 20 Mo et quotas par compte de 100 itinéraires ou 200 Mo, revérifiés avant publication. |
| Haute | Le XML importé utilisait le parseur général et les métadonnées GPX étaient reparsées côté navigateur par Leaflet-GPX. | `defusedxml`, refus des DTD/entités, coordonnées finies et bornées, taille et nombre de points contrôlés. Suppression de Leaflet-GPX : le navigateur reçoit uniquement des coordonnées JSON et du texte. GPX servis en téléchargement avec le type dédié et `nosniff`. |
| Moyenne | Une clé de session par défaut pouvait être utilisée si la configuration était oubliée. | Arrêt explicite au démarrage sans clé d'au moins 32 caractères ; `.env` protégé en mode 600 et exclu de l'image. Clé réelle conservée. |
| Moyenne | Le changement de mot de passe ne contrôlait pas la robustesse du nouveau mot de passe. Adresses normalisées ; index SQLite de recherche sur l'email. Vérification factice du mot de passe pour les comptes inconnus afin de limiter les différences de coût. |

Tests avec nom contenant une fermeture de script. |

OSRM utilise désormais le même client protégé. |

## Dépendances

`pip-audit 2.10.1` sur les 27 dépendances verrouillées, interrogé auprès de PyPI le 4 novembre 2026 : **aucune vulnérabilité connue signalée**. Les versions verrouillées venaient déjà d'être actualisées le 3 novembre ; elles ont été conservées. Ajout de `defusedxml==0.7.1`. Les outils de test et d'audit sont définis dans `requirements-dev.txt` et ne sont pas inclus dans l'image applicative.

Leaflet 1.9.4 est conservé, avec les empreintes d'intégrité publiées par le projet. Leaflet 2.0 est encore une préversion ; aucune migration vers cette version n'est nécessaire pour corriger les problèmes trouvés.

## Mesure de performance

Benchmark reproductible : 61 075 points de référence, parcours synthétique dense de 300 sommets près de Paris, rayon de 500 m. L'ancien algorithme teste 629 candidats contre les sommets ; le nouveau utilise tous les segments et les deux jeux de référence.

Mesure sur le RPi : **0,502 s avant, 0,089 s après**, soit environ **5,6 fois plus rapide** pour ce cas. Ancien résultat : 76 points ; nouveau résultat : 77, dont un point proche d'un segment mais absent de l'échantillonnage. Ce facteur dépend du parcours ; ce n'est pas une garantie sur tous les GPX. Les tests comparent également l'index à une recherche exhaustive et vérifient des distances connues.

## Limites et points à suivre

- Les tests automatisés ne remplacent pas la recette visuelle. Aucun courriel réel n'a été envoyé et les appels aux services tiers sont simulés dans les tests de sécurité.
- Le noyau actuel du RPi signale que les limites mémoire Docker ne sont pas appliquées. Les limites applicatives sont actives. Activer les cgroups mémoire nécessiterait une intervention distincte sur le système et éventuellement un redémarrage ; aucune modification du démarrage n'a été faite.
- Le suivi des tâches et les limites de requêtes restent en mémoire d'un seul worker. Un redémarrage perd les statuts ; plusieurs workers ou instances nécessiteraient une file de tâches et un stockage partagés.
- Les anciennes cartes HTML conservent leurs anciens résultats. Leur script historique reçoit un nonce compatible, mais elles doivent être recréées depuis les GPX pour bénéficier du calcul et du rendu actuels.
- Le budget de téléchargement est vérifié entre les lectures ; une résolution DNS ou une lecture réseau déjà engagée reste soumise aux délais du résolveur/système et au timeout réseau. Les tests ne prétendent pas imposer un délai mural strict au DNS.
- L'audit des dépendances Python n'est pas un scan des paquets système de l'image ou un audit de l'OS, du pare-feu et des comptes SSH du VPS/RPi. Il ne garantit pas l'absence de vulnérabilités inconnues.
